# Architecture

## System Overview

Journada is a decoupled full-stack application. The backend and frontend are separate codebases communicating over HTTP (REST API).

```
Browser (React SPA)
        │  HTTP / JSON
        ▼
Express API (Node.js + TypeScript)
        │  pg pool (max 20, 5s timeout)
        ▼
PostgreSQL (Supabase)
```

The frontend is a Vite SPA proxying `/api` and `/auth` to the backend in development. In production, static files are served independently and the backend URL is configured via environment variable. A service worker (generated by Workbox via `vite-plugin-pwa`) precaches the app shell and provides offline support.

**API route tree:**
- `/auth/*` — register, login, password reset
- `/api/sessions` — CRUD + `/search` + `/import` (bulk)
- `/api/profile` — GET / PUT
- `/api/intentions` — CRUD + `/current` + `/:id/journal`
- `/api/user-tags` — personal vocabulary CRUD (migration 008)

**Auto-migration:** Numbered SQL files in `backend_api/migrations/` run on server startup via the `runMigrations()` function in `app.ts`, tracked in the `schema_migrations` table.

## Request Flow (Authenticated)

```
1. User action triggers api.get/post/put/patch/delete()
2. api.ts injects Authorization: Bearer <token> from localStorage
3. Express receives request → authMiddleware.verifyToken()
4. verifyToken decodes JWT → attaches {id, email} to req.user
5. Controller runs business logic
6. Model executes parameterised SQL via pg.query()
7. Result returned as JSON
8. On 401 → AuthContext.authErrorHandler triggers logout()

Offline path (write operations only):
2b. fetch() throws (network unreachable) → api.ts enqueues request in IndexedDB
2c. Returns synthetic { _offline: true } response → UI proceeds optimistically
2d. On reconnect → useOnlineSync flushes queue, replaying requests in order
```

## PWA / Offline Support

Journada is an installable Progressive Web App. The service worker is generated at build time by `vite-plugin-pwa` (Workbox).

### Caching Strategies

| Resource | Strategy | Details |
|---|---|---|
| App shell (JS, CSS, HTML, icons) | Precache | Built into the service worker at `vite build` time; versioned per deploy |
| Google Fonts CSS | StaleWhileRevalidate | Serve from cache, revalidate in background |
| Google Fonts files (.woff2) | CacheFirst | Immutable font binaries; 1-year cache |
| API GET responses | NetworkFirst | 5-second network timeout; falls back to 24-hour cached response when offline |
| Navigation requests | navigateFallback | All non-API/auth routes serve cached `index.html` so React Router works offline |

### Offline Write Queue

When a write request (POST/PUT/PATCH/DELETE) fails due to a network error, `api.ts` enqueues it in IndexedDB via `offlineQueue.ts`. The queue:
- Returns a synthetic `{ _offline: true }` response so the UI proceeds optimistically
- Replays queued requests in order when connectivity returns (`useOnlineSync` hook)
- Deduplicates PATCH requests to the same path (journal autosave)
- Handles 401 during replay (keeps item in queue; user re-logs in and retries)

### Offline Read Cache

`apiCache.ts` provides a second-tier cache for GET responses, stored in IndexedDB (`journada-cache` database). This is transparent to all page components:
- **On successful GET**: response is cached (fire-and-forget, non-blocking) keyed by full URL path including query params
- **On failed GET (offline)**: if Workbox has no cached response, `api.ts` falls back to the app-level cache before throwing
- **24-hour expiry**: stale data is better than no data, but not infinitely stale
- **Reconnect refetch**: `useOnlineRefetch` hook listens for `journada:online-ready` event (dispatched by `useOnlineSync` after write queue flush) and re-calls the page's fetch function

### Optimistic Pending Sessions

Sessions logged while offline appear immediately in the UI (calendar, week view, analytics) via a localStorage-backed pending sessions store:
- **On offline session log**: `LogSessionForm` saves a `SessionSummary` (with temp `pending-*` ID) to `pendingSessions.ts`
- **Display**: all pages merge pending sessions with fetched/cached sessions via the `usePendingSessions` hook
- **On reconnect**: pending sessions are cleared automatically when `journada:online-ready` fires — fresh server data (which now includes the synced sessions) takes over

### Manifest

`public/manifest.webmanifest` — `start_url: "/home"`, `display: "standalone"`, `orientation: "portrait"`. Icons at 192px, 512px, and 512px maskable.

### Service Worker Registration

Registered in `main.tsx` via `virtual:pwa-register`. Uses `registerType: 'autoUpdate'` — new service workers activate immediately without a user prompt.

## Notification Scheduler

The API process also runs a 1-minute `node-cron` tick that fans out class-time push notifications. See [Implementations.md § Web Push](Implementations.md#web-push-class-times-notifications) for the full pipeline.

**Single-instance assumption:** the dedup set that prevents double-fires within a minute is in-memory. If the API service is ever scaled to multiple Railway replicas, hoist the scheduler to a dedicated worker service or move dedup to a Postgres advisory lock / `notification_sends` ledger. Today there's a single replica, so this is a non-issue.

**Boot sequence:** `server.ts` calls `runMigrations()` first, then `startNotificationScheduler()`. The scheduler no-ops cleanly if VAPID env vars are missing — the API still serves CRUD for class schedules so users can configure schedules without notifications wired up yet.

**Required env vars (Railway):** `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`. Generate with `npx tsx backend_api/scripts/generate-vapid-keys.ts`.
